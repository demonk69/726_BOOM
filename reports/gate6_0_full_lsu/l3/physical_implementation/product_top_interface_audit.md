## LSU Transaction Ownership

Loads allocate transaction IDs only after checking active load-queue owners. `lsu_allocate_transaction_id` probes `next_transaction_id` and rejects IDs already present in active pending load owners (`src/lsu.cpp:158` through `src/lsu.cpp:169`). A new external load writes the DMEM request, records the transaction ID in the ROB and load queue, sets pending metadata, and increments `outstanding_load_count` (`src/lsu.cpp:201` through `src/lsu.cpp:226`).

Responses are matched by transaction ID against exactly one valid pending load-queue owner before completion is accepted (`src/completion.cpp:81` through `src/completion.cpp:137`). Completion validation re-checks ROB ownership, load-queue generation, allocation ID, and transaction ID (`src/completion.cpp:167` through `src/completion.cpp:203`).

This means a physical wrapper must preserve `DmemResponse.transaction_id` without rewriting ownership semantics.

## Commit Trace

Commit entries are generated by `rob_commit_module` only when the commit-trace stream can accept them. Exception commits write a trace record at `src/commit.cpp:200` through `src/commit.cpp:208`. Normal commits populate register and memory fields, then write the trace entry at `src/commit.cpp:261` through `src/commit.cpp:283`.

The wrapper must either consume `commit_trace_out` with backpressure semantics or intentionally compile/build a product mode that removes or internalizes this debug trace. Exporting the raw 768-bit `CommitEntry` payload to package pins is the largest single I/O contributor.

## Top Variants

`boom_core_pf4_rtl_top` is explicitly marked test-only in source comments and adds `test_seed_in` for focused predictor/FTQ RTL verification (`src/boom_core_top.cpp:155` through `src/boom_core_top.cpp:218`). It is not a deployable product wrapper.

`boom_core_step_top` executes one cycle per call and uses the same raw stream/status interface (`src/boom_core_top.cpp:220` through `src/boom_core_top.cpp:262`). It is useful for test/harness integration but does not solve package I/O pressure.

## Wrapper Requirements

A feasible physical wrapper must:

1. Keep the core clock/reset sequencing compatible with `ResetControllerState`.
2. Preserve AXIS ready/valid backpressure on IMEM, DMEM, and commit trace paths.
3. Preserve DMEM transaction IDs end to end so out-of-order responses return to the correct load-queue owner.
4. Preserve commit-trace order or explicitly define a product build mode that disables/externalizes tracing without changing architectural commit behavior.
5. Avoid exporting wide HLS payload structs directly to package pins.
