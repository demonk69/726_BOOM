# LSU Interface Contract

Current request is ready/valid through `pipe.dmem_req`: 32-bit transaction ID, 8-bit ROB index/command/size/masks/branch metadata, store/load flags, and 64-bit address/data aliases. Response is ready/valid through `pipe.dmem_resp`: transaction ID, data aliases, exception and cause aliases. Load and committed-store producers share this FIFO; cycle order is completion, LSU load issue, then commit store (`boom_core_step.cpp:23-32`). Thus a newly enqueued load procedurally gets first opportunity, while an older store blocks younger loads and a head store stalls if the stream becomes full.

For L3 multi-outstanding operation, the minimal external extension is not a wider payload but a frozen tagged protocol: preserve the unique 32-bit request/response transaction ID, permit multiple accepted requests, require exactly one terminal response per accepted load, and define that killed/stale responses are still returned and consumed/dropped. Internally retain `{lq_index,lq_generation,rob_idx,rob_allocation_id,transaction_id}`. A finite generation width is safe only with a protocol bound preventing an old response from surviving 65536 reuse events of one slot.

Known later-gate limitations are explicit: transaction-ID wrap is only probabilistically/lifetime safe without that bound, and stores have no response/acknowledgment path, so an external store access fault cannot currently be reported after request acceptance. These do not block L1 state ownership work but must be resolved by the L3/L5 interface contract before claiming a fault-capable full LSU.
